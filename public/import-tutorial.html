Building “Import your holdings”

A tutorial covering how this feature reads a broker statement entirely in the browser, for another developer who wants to implement something similar. SIT774 Task 10.3HD, implementing the Task 7.3HD proposal.

Try it yourself on the Register page, under “Your holdings.” This page explains how it works underneath.

The problem this solves

StockWise's Register page promises it is read‑only: it never connects to a trading account. That rules out the obvious shortcut — a “Connect your broker” button using an API or OAuth flow — since that would mean StockWise holding an access token and an ongoing connection to a live financial account. The alternative is to let the user supply the statement their broker already gives them (a CSV or PDF export) and read it locally, so the file, and anything extracted from it, never has to leave the device during parsing.

Three pieces, three files

Files that make up this feature
FileRole
register.html The “Your holdings” panel: a Choose File button, a drop zone, a progress region, and the review table these scripts fill in.
js/holdings-import.js Runs on the main thread. Opens the file (two different ways, below), hands its contents to the worker, and renders the review table from what comes back.
js/holdings-import-worker.js A Web Worker. Does the actual parsing — CSV field-splitting, and the PDF row-grouping heuristic — off the main thread.

Opening the file: two APIs, on purpose

CSV files are opened with window.showOpenFilePicker(), the File System Access API. It is Chromium-only at the time of writing, so it is feature-detected, not assumed: 

var supportsFileSystemAccess = typeof window.showOpenFilePicker === 'function';

Everything else — PDF files, and any browser without that API (Safari, Firefox) — falls back to a plain <input type="file"> plus a click on it. Both paths end up with the same thing, a File object, so the rest of the code does not need to know which one supplied it. Drag-and-drop onto the panel is wired up too, but only as a third way to reach the same handleFile(file) function — the button is never the only path, which matters for a keyboard or screen-reader user (more on that below).

Why parsing happens in a Web Worker

A statement can be a large file, and turning it into structured rows is CPU work. Doing that on the main thread would freeze the page — scrolling, typing, clicking, all of it — until parsing finished. A Worker runs JavaScript on a separate thread, so the page stays responsive: 

worker = new Worker('js/holdings-import-worker.js');
worker.postMessage({ type: 'csv', text: fileText });
worker.addEventListener('message', function (event) {
  // event.data is { type: 'result', rows: [...] }
});

The worker cannot touch the DOM at all — that is the trade-off for running off-thread — so it only ever sends back plain data (an array of row objects), and holdings-import.js is the only place that builds HTML from it.

CSV: the confident path

CSV is a solved problem here: split on commas (respecting quoted fields), match a header row's column names against a few likely spellings (name/holding/security, and similarly for ticker and quantity), and read each row against those columns. A row only gets flagged Needs review if the name is blank or the quantity is not a number — otherwise it is trusted.

PDF: the hard part, honestly

A PDF has no built-in idea of a table. pdf.js (the library behind Firefox's own PDF viewer) hands back a flat list of text runs, each with an x/y position on the page — not rows, not columns, just positioned text. Turning that into holdings is a two-step heuristic:

  1. Group into lines. Runs whose y-coordinate is within a few points of each other are treated as the same line. This has to be done per page, so a line near the bottom of page 1 is never merged with one near the top of page 2.
  2. Split each line into columns. Within a line, a horizontal gap bigger than a threshold is treated as a column boundary. The column that is purely numeric becomes the quantity; the column with real letters in it becomes the name; anything short and in capitals becomes a ticker guess.

A line that does not produce both a name-like and a quantity-like column — a page title, a column heading, a footer — is simply not treated as a row, rather than guessed at. A line that produces more columns than expected is kept, but flagged Needs review, since that usually means a name wrapped onto two lines and the heuristic split it awkwardly.

This is a genuine limitation, not a bug to be fixed away: company names that wrap onto a second line, statements where the header does not repeat on page two, and multi-column layouts where text extraction order does not match reading order can all defeat this heuristic. Different brokers do not share a statement template, and a broker can change its layout without notice. That is exactly why nothing here is auto-committed — see the review table, next.

A note on where pdf.js's own worker fits in

pdf.js already manages its own internal worker (pdf.worker.js) for the expensive binary PDF parsing step. Rather than nesting a second copy of pdf.js inside holdings-import-worker.js — a fragile worker-inside-a-worker setup for no real benefit — this implementation calls pdf.js from the main thread (it is already off-thread for the heavy part), and hands only the lightweight extracted text items to the custom worker, which does the row-grouping heuristic. That CPU-bound step has no built-in pdf.js function to do it, and is the part actually worth moving off the main thread here.

The review table: nothing is auto-committed

Every row, from either CSV or PDF, lands in an editable table before anything is saved — this is a usability requirement, not a nice-to-have, because it is the only honest way to ship a parser that will sometimes be wrong. Confidence is shown per row, not as one pass/fail result for the whole file: a name field can be typed over, a bad quantity can be corrected, an entire row can be removed. Manual entry (“Add a holding manually”) adds a blank row into the exact same table, so import and manual entry are two ways into one review step, not two separate features.

Clicking Save holdings is the only point past which rows are treated as confirmed. StockWise's register form has no backend holdings storage yet, so this demonstrates the interaction itself: the moment nothing can be auto-committed past, matching what the page's existing consent checkboxes already govern for manually-typed holdings.

Usability, accessibility and performance

Usability

Partial success is a normal outcome, not an error state: if seven of ten rows parse cleanly, the user sees seven filled rows and three flagged ones, never a rejected file. CSV is nudged as the confident path when a PDF produces low-confidence rows.

Accessibility

Drag-and-drop is a convenience, never the only path — the Choose File button is a real, keyboard-focusable, screen-reader-operable control. Progress updates use aria-live="polite", announced at meaningful steps rather than on every percentage tick. The review table is a real, properly headed <table>, the same convention already used for the plan comparison table on Plans & Services.

Performance

Parsing runs in a Web Worker specifically so a large file does not block the interface while it is read. The trade-off is the added complexity of message-passing between the worker and the page — justified here because file size and parse time are outside the site's control.

Try it with your own file

A CSV needs a header row containing name, ticker and quantity (or close spellings — units, shares, symbol and similar are recognised too). Any PDF with a holdings-style table is worth trying; the review table will show exactly what was found, confidence and all.
